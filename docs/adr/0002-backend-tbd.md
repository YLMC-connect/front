# ADR 0002 — 백엔드 선택 보류 (Mock-first)

> 상태: 수락 (Accepted, “결정 보류” 자체를 결정함) | 작성일: 2026-05-08 | 재검토 시점: Phase 6 (인증) 진입 직전

## 컨텍스트

YLMC Connect 는 4 개 도메인 (장터 · 소모임 · 삶공부 · 기도) + 인증 + v2 실시간 커뮤니케이션을 포함한다. 초기 시점에 백엔드 플랫폼을 확정하면 다음 위험이 있다.

- **요구사항 미확정** — UI 를 만들어 봐야 실제 데이터 모델이 굳는다. PLAN.md “🗃 데이터 타입 설계” 도 첫 도메인 작업 후 미세 조정될 가능성이 큼.
- **운영 주체 미정** — 교회 자체 인프라 / 외부 BaaS / 자체 호스팅 중 어느 쪽이 운영 가능한지(서버 비용 · 관리 인력) 가 정해지지 않음.
- **개인정보 정책 미정** — 기도제목 본문 · 익명 처리 · 만료 정책에 따라 데이터베이스 선택 폭이 달라짐. 교회 내부 검토 필요.
- **인증 방식 미정** — 자체 가입 / 교적 시스템 연동 / SSO 중 어떤 형태인지 결정되어야 백엔드 선택이 가능.

이 상황에서 “일단 Firebase 로 시작” 같은 결정은 나중에 마이그레이션 비용을 만든다. 차라리 결정을 **명시적으로 보류** 하고, 보류 기간 동안 백엔드 무관한 코드를 쌓는 편이 안전하다.

## 결정

**Phase 5 종료까지 백엔드 플랫폼을 선택하지 않는다.** 대신 다음 전략을 채택한다.

### Mock-first 개발

- 모든 데이터 페칭은 `src/services/<domain>Service.ts` 함수를 거친다.
- Phase 1~5 동안 이 함수들은 `src/mocks/` 의 정적 데이터를 (필요 시 `setTimeout` 으로 비동기 흉내) 반환한다.
- TanStack Query 훅 (`src/hooks/use*.ts`) 은 **백엔드 교체 시점에도 변경되지 않는다** — 교체 영향은 `services/` 한 레이어로 격리된다.

### 후보 평가는 Phase 5 종료 직후

Phase 6 (인증) 진입 전에 별도 ADR 0003 으로 다음 후보를 비교한다 (현 시점 잠정 후보군 — 본 ADR 은 비교를 강제하지 않음, 후보 자체도 그때 재검토):

| 후보 | 강점 | 약점 |
|---|---|---|
| **Supabase** | Postgres + Realtime + Auth + Storage 통합. RLS 로 권한 모델 명확 | 자체 호스팅 시 운영 부담 / 관리형은 비용 |
| **Firebase** | 익숙도, 무료 티어 관대, 푸시 통합 | NoSQL 모델이 관계형 도메인(소모임 멤버 · 삶공부 이력)에 적합도 낮음 |
| **자체 백엔드** (Node/Nest 등) | 완전한 통제 | 운영 인력 필요, 초기 속도 느림 |

> 본 ADR 은 위 후보 중 하나를 “기울이지” 않는다. Phase 6 직전의 운영 환경 / 정책에서 다시 판단.

### 결정 트리거 (보류 종료 조건)

다음 중 하나라도 발생하면 즉시 ADR 0003 을 작성하여 보류를 해제한다.

1. Phase 5 (기도) 완료 — 모든 도메인 데이터 모델이 코드로 한 번 실증됨.
2. v2 실시간 커뮤니케이션의 인프라 의존성이 다른 도메인보다 먼저 가시화 — 실시간 백엔드가 다른 도메인을 강제하면 조기 결정.
3. 외부 인증 시스템 (교적 SSO 등) 연동 요구가 들어옴.
4. 베타 테스터에게 Mock 이 아닌 실제 데이터로 운영해야 함.

## 영향 — 보류 기간 동안 지켜야 할 규칙

- **services/ 외부에서 fetch / axios 직접 호출 금지.** 모든 네트워크 경로는 services/ 함수를 거친다.
- **TanStack Query 의 `queryFn` 에서 직접 Mock 배열을 참조하지 않는다.** 항상 services/ 함수를 호출한다 — 그래야 Phase 7 에서 services/ 만 교체하면 끝난다.
- **타입은 백엔드 응답 형태와 1:1 일치하도록 설계한다** (PLAN.md 의 `PaginatedResponse<T>` 등). Mock 도 이 형태를 지켜야 한다.
- **인증 토큰 저장은 `expo-secure-store`** 로 작성한다 — 백엔드가 정해지지 않았어도 저장 인터페이스는 미리 안정화 가능.
- **백엔드 의존 기능 (실시간 알림 · 푸시 · 파일 업로드) 의 코드 작성을 본 ADR 해제 전까지 미룬다.** Mock 으로 흉내 내려는 시도가 오히려 부채가 된다.

## 고려했지만 채택하지 않은 대안

| 대안 | 기각 사유 |
|---|---|
| **지금 Firebase 로 확정하고 시작** | 데이터 모델 · 권한 정책 · 비용 구조를 검증하기 전 결정. 후환 비용이 “Mock-first 의 일시적 어색함”보다 훨씬 큼. |
| **지금 Supabase 로 확정하고 시작** | 위와 동일. 단, Supabase 가 유력 후보임은 ADR 0003 시점에 다시 평가. |
| **MSW (Mock Service Worker) / json-server** 도입 | RN 환경에서 추가 설정이 필요한데, services/ 함수가 정적 Mock 을 반환하는 방식만으로 충분. 추가 인프라는 부채. |
| **Mock 없이 백엔드 결정까지 UI 작업 보류** | 실제로 화면을 만들어야 데이터 모델이 굳음. 보류는 “UI 까지 보류” 가 아니라 “백엔드만 보류” 임. |

## 변경 이력

- 2026-05-08 — 최초 수락. 백엔드 플랫폼 결정을 Phase 6 직전까지 명시적으로 보류. Mock-first 전략과 services/ 격리 원칙을 영속화.
